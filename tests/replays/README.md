# Replay corpus

Deterministic input scripts that drive the real game through as much of its code as possible. They serve two
purposes:

- **Coverage traces** for the recompiler (`tools/trace/run_corpus.py`, results in
  `docs/re-notes/trace-coverage.md`).
- **Regression checks**: CTest `replay_<name>` plays each script and compares frame and audio hashes with
  `<name>.hashes`.

Only scripts and hashes are committed. Game data stays in `generated/assets/`.

The scripts are generated by `tools/trace/make_replays.py`, which also holds the per-replay notes and the
measured timings. Edit the generator, not the `.txt` files, then re-record the hashes (see below).

## Script format (`x2recomp --input-script FILE`)

There is one event per line, and `#` starts a comment. FRAME is an absolute frame number (0-based, the frame
the event applies to), or `+N` relative to the previous line's frame.

| Line | Meaning |
|---|---|
| `FRAME fire [N]` | hold fire (port 2) for N frames (default 3) |
| `FRAME key HEX` | press Amiga raw key HEX; it is released 2 frames later (`19` P = pause, `45` ESC, `40` SPACE) |
| `FRAME joy DIRS [N]` | hold directions for N frames (default 1). DIRS is any of `U D L R F`, where F is fire. |
| `FRAME poke ADDR VALUE[.b\|.w\|.l] [N]` | **coverage only**: write chip RAM at the start of N frames (default 1). The default size is `.w`. |
| `FRAME pokeobj HANDLER OFFSET VALUE[.b\|.w\|.l] [N]` | **coverage only**: the same write at OFFSET into every object on the game's hittable-object list whose hit handler (+`$A`) is HANDLER, e.g. a boss's HP at +`$32` (see below) |
| `frames N` | the total number of frames to run |

`fire`, `key` and `joy` lines may end with `every P until G`: the event then repeats every P frames up to
frame G.

The same events are available on the command line as `--fire`, `--key`, `--joy` and `--poke`. Directions and
fire from all active events are OR-ed together each frame.

All replays start from power-on. Each is at most 6000 frames (2 minutes at 50 Hz).

### Pokes and the variables they use

Pokes exist only so that coverage runs can reach late game states inside the frame budget. They are never
applied unless a script or `--poke` asks for them, and a run with pokes prints `coverage pokes active`. The
addresses below are from the Ghidra listing (`generated/lane-d2/ghidra_*.lst`). The evidence for each is in
`docs/re-notes/trace-coverage.md`.

| Variable | Use in the scripts |
|---|---|
| `$CC6.w` energy (max `$27`) | held at `$27` for invincibility; set to 1 so the next hit kills |
| `$CCA.w` ships, `$CF0.w` credits | held at 3; set to 1 to force the death, continue and game-over paths |
| `$E04.w` level (1-5), `$A07.b` level-complete flag | `$E04=N-1` and `$A07=$FF` make the main loop's own end-of-level path load level N |
| `$A6C.b` shop request | `$FF` makes the main loop load the shop (`$7B8C` -> `$8FF2`) |
| `$CD0`/`$CEA`/`$CCE.w` scroll position, `$CE8.w` lower scroll clamp, `$CD2`/`$CD4.w` event cursors | fast-forward and jumps through a level |
| `$C92.l` score, `$C9A.l` cash | high-score entry, and buying in the shop |
| `$3F040.w` ship y | `boss1`: `$90` for 20 frames, so `$CD0` + y < `$A80` triggers the mid-level shop at once |
| `$4F2`/`$4F4.w` shop cursor column/row | UI only: put the cursor on SELL or EXIT before a fire, in case a purchase dialog swallowed a move |
| obj+`$32.w` HP, via `pokeobj` | held at 1 for a boss, so the first shot that the boss's own hit handler accepts runs its real death code. Handlers: level 1 `$561DA`, level 4 eyes `$55A1C` and head `$559D6`, level 5 guardians `$561D2` and the structure the core damages (`$E48`) |
| `$D7A.w` level-5 guardians left | `ending_natural`: set to 1 after level 5's end event has set it to `$12`, so the one guardian in reach finishes the set and the core becomes hittable (`docs/re-notes/ending-flow.md`) |

`pokeobj` walks the list the way the collision loop `$306E` does: head pointer `$B4C`, next object at +`$12`, and
an object whose type word (+0) is 0 ends the list. Type-`$B8` groups let the collision loop skip their members
through +`$5A`; following +`$12` alone visits the members too. The walk stops after 1024 objects
(`x2::kObjWalkLimit`), so a corrupt or self-linked list (the `obj_alloc` hang below) cannot hang it. The smoke
test `pokes` checks the walk on a synthetic list, including a group and a self-linked node.

### Boss defeats: what is reached and what is not

There is no state-snapshot facility, so a chain of levels has to fit the 6000-frame budget of one replay. A level
scrolls at about 0.28 rows per frame (about 16,000 frames per level), so every boss replay fast-forwards the scroll
position, and only level 1 to level 2 fits in one replay. Levels 2-5 are reached with `goto_level` (a `$E04`
poke into the game's own end-of-level path).

| Level | Boss | Result |
|---|---|---|
| 1 | nautilus, hit handler `$561DA` (vulnerable box x `$98-$A7`, only while `$D8B` is set) | **defeated** in `boss1`: death `$5621E`, bonus, `$A07`, shop, level 2 |
| 2 | spider `$5685A` | not defeated. Its box stays inactive (x = `$3E8`) until the player's level position (`$3F040` + `$CD0`) is at most `$B0` (`$56C0E`); the ship could not get above the web, and position pokes upset the scroll. |
| 3 | `$5525A` sets `$A07` once `$D92` and `$D93` are both set and `$CD0` <= `$D0` | not defeated; the handlers that set `$D92`/`$D93` were not identified |
| 4 | eyes `$55A1C`, head `$559D6` | eyes destroyed in `level4_boss`; the head's box stays above the screen top |
| 5 | the arena at the end of the level: a structure, 18 guardian pods (hit handler `$561D2`, counted in `$D7A`) and a core (hit handler `$562A6`) that is only hittable once `$D7A` is 0 | **defeated** in `ending_natural`: the core's death code `$562DC` spawns the shop capsules through `$E6C` and sets `$A07` at `$5631E`; the game then requests the shop itself, sets `$8FEC`, plays the ending and loops back to level 1. `$D7A` is poked to 1 because only one of the 18 pods is in reach inside the frame budget. An earlier attempt reported "no boss"; see `docs/re-notes/ending-flow.md` section 2. |

## Health rules

A replay is kept only if it runs cleanly: no restart through `$7032`, no frozen picture, no endless
`obj_alloc` loop, and no write into executed code (the tracer reports `code_writes` and `code_changes`). These
plan variants broke the game and were dropped. All three are poke artefacts:

- **Scrolling far in one step without moving the event cursors** fires every skipped event at once. In level 3
  this exhausted the object pool, and `obj_alloc` (`$2436`) then looped forever on a list node linked to
  itself (list `$B4C`). Plain jumps now move `$CD2`/`$CD4` too, and the flood replays leave level 3 out.
- **Moving the scroll position below the level's lower clamp `$CE8`** (a mid-boss scroll lock) gives the scroll
  update at `$7A0A` a huge delta. The background row `$436` then leaves `0..$BF`, and `blit_objects_main`
  (`$17D6`) blits about 140 KB from `$54E0C` onwards, over the level module. The game then executes the
  overwritten header and restarts. Fast-forward now lowers `$CE8` with each step.
- **Level 5 below about `$560`**: the level moves the position back up by itself, and the next jump down crashed
  in the same way. Level 5 fast-forward stops at `$600`.

## Timing model and re-recording (Phases 6c and 6d)

Re-recorded again in Phase 6d, when the copper's DMA slots, the interrupt exception's bus cycles and MOVEM's
extra read were added to the accurate model (`docs/re-notes/timing.md` §9). The copper takes 19 chip-bus slots
per frame at line 0 and again at the buffer swap, so logic steps are slightly longer and the random sequence
follows a different path from the title onwards. Every `.hashes` file, `tests/golden/modern_midpoints.txt` and
the `cdtv_game` audio hashes changed; `tests/golden/game_frames.txt`, `tests/golden/modern_wide.txt` and the
`cdtv_game` cue goldens did not. No script needed a change: every replay still reaches the states listed above,
and the trace corpus reaches the same code except five instructions in `level2` (82.79 % to 82.76 % of the
traced modules).

## Timing model and re-recording (Phase 6c)

All `.hashes` files and `tests/golden/game_frames.txt` were re-recorded when the accurate timing model became
the default (`docs/re-notes/timing.md` §8). The model changes the length of the game's logic steps (the blitter
takes time, the CPU waits for the chip bus, the frame has 313 lines), so steps end on other VBLs, inputs land in
other steps and random outcomes differ: every frame and audio hash after the first few seconds changes, while
each replay still takes the same path (the same disc loads, shops, levels and endings; checked by running every
replay with `--timing fast` and `--timing accurate`). `--timing fast` reproduces the Phase 6b behaviour, but the
committed hashes are for the default.

One script needed a change to stay on its path with both models: in `boss1` the mid-level shop trigger is
`$CD0` + ship y (`$3F040`) < `$A80`; with the ship at its start (y `$B0`) and the scroll poked to `$9E0` it
waited for the scroll to move 16 rows, and a scroll lock at `$9D3` stopped it short of that with the accurate
model. The ship's y is now poked to `$90` for 20 frames 60 frames after the scroll jump.

## Regenerate and re-record

```
python3 tools/trace/make_replays.py                          # rewrite tests/replays/*.txt
python3 -I tools/trace/run_corpus.py --record-hashes --no-trace   # rewrite tests/replays/*.hashes
python3 -I tools/trace/run_corpus.py                         # traces + generated/trace/{coverage,indirect_targets,report}.json
```

The hashes are FNV-1a 64 values:

- the frame hash covers the rendered 320x256 RGBA frame (`--hash-at`);
- the audio hash covers all Paula output samples up to the end of that frame (`--audio-hash`).

Both are bit-exact and deterministic. Two consecutive recordings were identical.

## Other game builds

`tests/replays/power-pack-2234/` and `tests/replays/compilation-1762/` hold the same 19 replays' hash manifests for
the Power Pack (SPS 2234) and Bombuzal + Xenon 2 (SPS 1762) builds (`docs/re-notes/build-variants.md`). Their assets
come from `tools/variants/write_assets.py`; CTest runs them as `build_<build>_<replay>` and skips them without the
assets. Re-record with `tools/trace/run_corpus.py --assets DIR --record-hashes --no-trace --hashes-out DIR`.

## The CDTV release

`tests/replays/cdtv/` holds 23 scripts of its own and their hash manifests: the CDTV release has a different front end (a
joypad-mode page, title and guide pages, a 1/2-player menu), so the disk build's scripts do not apply to it, and its frames and audio
are not comparable with the disk build's. The scripts come from `tools/trace/make_cdtv_replays.py` (edit that, then re-record), the
states they reach are measured with `tools/trace/cdtv_probe.py`, and `docs/re-notes/cdtv-replays.md` has the variable map, the boss
handler table, what each replay reaches and what it does not. The four earliest scripts (`attract`, `menus`, `level1_play`,
`level1_special`) keep the slow front end (a fire every 150 frames, level 1 at about frame 2105); the others use a faster one (a fire
every 40 frames; the menu takes input from about frame 1450; 2 PLAYER GAME is one `down` at 1490; level 1 is controllable from about
frame 1760), which leaves more of the 6000 frames for play.

build's object-list head (`BuildInfo::var_objlist`: `$B4C` in the disk builds, `$B52` in the CDTV release).
