# Replay corpus

Deterministic input scripts that drive the real game through as much of its code as possible. They serve two
purposes:

- **Coverage traces** for the recompiler (`tools/trace/run_corpus.py`, results in
  `docs/re-notes/trace-coverage.md`).
- **Regression checks**: CTest `replay_<name>` plays each script and compares frame and audio hashes with
  `<name>.hashes`.

Only scripts and hashes are committed. Game data stays in `generated/assets/`.

The scripts are generated by `tools/trace/make_replays.py`, which also holds the per-replay notes and the
measured timings. Edit the generator, not the `.txt` files, then re-record the hashes (see below).

## Script format (`x2recomp --input-script FILE`)

There is one event per line, and `#` starts a comment. FRAME is an absolute frame number (0-based, the frame
the event applies to), or `+N` relative to the previous line's frame.

| Line | Meaning |
|---|---|
| `FRAME fire [N]` | hold fire (port 2) for N frames (default 3) |
| `FRAME key HEX` | press Amiga raw key HEX; it is released 2 frames later (`19` P = pause, `45` ESC, `40` SPACE) |
| `FRAME joy DIRS [N]` | hold directions for N frames (default 1). DIRS is any of `U D L R F`, where F is fire. |
| `FRAME poke ADDR VALUE[.b\|.w\|.l] [N]` | **coverage only**: write chip RAM at the start of N frames (default 1). The default size is `.w`. |
| `frames N` | the total number of frames to run |

`fire`, `key` and `joy` lines may end with `every P until G`: the event then repeats every P frames up to
frame G.

The same events are available on the command line as `--fire`, `--key`, `--joy` and `--poke`. Directions and
fire from all active events are OR-ed together each frame.

## Replays

All replays start from power-on. Each is at most 6000 frames (2 minutes at 50 Hz).

| Replay | Pokes | Covers |
|---|---|---|
| `attract` | no | title, credits pages, high-score table, two full attract cycles |
| `menu_2p` | no | SELECT menu moves, MUSIC on/off, 2-player game (both players' turns), P pause/unpause, SPACE, ESC to the title, 1-player restart |
| `level1_play` | no | 1-player level 1 with real movement and shooting, deaths, high-score entry and the continue prompt |
| `game_over` | yes | death with a high score, high-score name entry, continue, then the last credit lost: GAME OVER |
| `shop` | yes | level-1 mid-level shop reached through the scroll trigger, the SELL phase, buying the stock, playing with the new weapons |
| `shop5` | yes | level-5 shop (full stock and extra text) with large cash, buying over all 20 cells |
| `level1_ff` | yes | level 1 fast-forwarded: first half, mid-level shop, second half, the boss |
| `level2`, `level3`, `level4`, `level5` | yes | level N reached through the end-of-level path, then fast-forwarded from `$1180` towards the end (level 5 only down to `$600`) |
| `level1_flood`, `level2_flood`, `level4_flood` | yes | one-step scroll jumps that fire each skipped stretch's events at once, so many enemy types are alive together |
| `ending` | yes | level-5 shop requested late in the level, so the game sets its ending flag `$8FEC` and slot 6 plays the ending text |

### Pokes and the variables they use

Pokes exist only so that coverage runs can reach late game states inside the frame budget. They are never
applied unless a script or `--poke` asks for them, and a run with pokes prints `coverage pokes active`. The
addresses below are from the Ghidra listing (`generated/lane-d2/ghidra_*.lst`). The evidence for each is in
`docs/re-notes/trace-coverage.md`.

| Variable | Use in the scripts |
|---|---|
| `$CC6.w` energy (max `$27`) | held at `$27` for invincibility; set to 1 so the next hit kills |
| `$CCA.w` ships, `$CF0.w` credits | held at 3; set to 1 to force the death, continue and game-over paths |
| `$E04.w` level (1-5), `$A07.b` level-complete flag | `$E04=N-1` and `$A07=$FF` make the main loop's own end-of-level path load level N |
| `$A6C.b` shop request | `$FF` makes the main loop load the shop (`$7B8C` -> `$8FF2`) |
| `$CD0`/`$CEA`/`$CCE.w` scroll position, `$CE8.w` lower scroll clamp, `$CD2`/`$CD4.w` event cursors | fast-forward and jumps through a level |
| `$C92.l` score, `$C9A.l` cash | high-score entry, and buying in the shop |
| `$4F2`/`$4F4.w` shop cursor column/row | UI only: put the cursor on SELL or EXIT before a fire, in case a purchase dialog swallowed a move |

## Health rules

A replay is kept only if it runs cleanly: no restart through `$7032`, no frozen picture, no endless
`obj_alloc` loop, and no write into executed code (the tracer reports `code_writes` and `code_changes`). These
plan variants broke the game and were dropped. All three are poke artefacts:

- **Scrolling far in one step without moving the event cursors** fires every skipped event at once. In level 3
  this exhausted the object pool, and `obj_alloc` (`$2436`) then looped forever on a list node linked to
  itself (list `$B4C`). Plain jumps now move `$CD2`/`$CD4` too, and the flood replays leave level 3 out.
- **Moving the scroll position below the level's lower clamp `$CE8`** (a mid-boss scroll lock) gives the scroll
  update at `$7A0A` a huge delta. The background row `$436` then leaves `0..$BF`, and `blit_objects_main`
  (`$17D6`) blits about 140 KB from `$54E0C` onwards, over the level module. The game then executes the
  overwritten header and restarts. Fast-forward now lowers `$CE8` with each step.
- **Level 5 below about `$560`**: the level moves the position back up by itself, and the next jump down crashed
  in the same way. Level 5 fast-forward stops at `$600`.

## Regenerate and re-record

```
python3 tools/trace/make_replays.py                          # rewrite tests/replays/*.txt
python3 -I tools/trace/run_corpus.py --record-hashes --no-trace   # rewrite tests/replays/*.hashes
python3 -I tools/trace/run_corpus.py                         # traces + generated/trace/{coverage,indirect_targets,report}.json
```

The hashes are FNV-1a 64 values:

- the frame hash covers the rendered 320x256 RGBA frame (`--hash-at`);
- the audio hash covers all Paula output samples up to the end of that frame (`--audio-hash`).

Both are bit-exact and deterministic. Two consecutive recordings were identical.
