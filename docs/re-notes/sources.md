## Classification

- Two-disk sets: BS1 `[t +3]` (A1+A2, z06+z08, Xenon2.zip), BS1 DJ99 hack (z04+z05). Disk 1 is a standard OFS boot disk (startup-sequence), disk 2 is a headerless raw data disk the game reads itself.
- Cracked retail disk 1 (the game image stored plain at `$70C00`; the standard disc 2 is still needed): PNA, PNA[a], QTX, Black Monks (also Flashtro and Predators, below). One-disk crunches (the game as a crunched memory snapshot plus six crunched data files that are the standard disc 2): VF, VF[a], Black Monks `[h][t +36]`. Details and recovery recipes: `docs/re-notes/cracks.md`.
- Trained: BS1 `+3` (trainer menu in the `BS1` loader file, 30516 bytes, started from `s/startup-sequence`: `add21k`, `BS1`, `XENON-II`). DJ99 replaces the BS1 loader with `DJ99` (88124 bytes, Red Sector Demomaker intro, text "XENON II TRAINER FROM BAMIGA SECTOR ONE, FIXED FOR UAE ON 25.06.97 BY DJ99", "TWO DISK PACK WORKING ON UAE, A LAZARUS RELEASE IN 1997").
- Cracked: all of them are cracks of the 1989 ImageWorks release (cracker tag in name). No image is an untouched original.
- The RNC strings found by a naive scan of PNA/QTX/BM are a Rob Northen copylock filler pattern (`RNC\x00 RNC\x01 RNC\x02 ...`), not RNC-packed data.

## Main executable and key diffs

BS1 disk 1 files (A1/z06): `XENON-II` (205784 bytes, one 205724-byte chip-RAM CODE hunk + 4-byte BSS), `BS1` trainer loader (30516), `c/add21k` (280), `devs/System-Configuration` (232), `s/startup-sequence` ("add21k\nBS1\nXENON-II\n").

Main exe `XENON-II` / `Xenon2`: SHA1 `778cf75e75d7e1b2036f4d68f8a557b69e99a817`, byte-identical in A1, z06, z07 and the DJ99 disk (z04, file `Xenon2`). Entropy 7.78 bits/byte: the body is packed/encrypted behind a ~0x130-byte stub (first instructions `lea $134(pc),a0; adda.l #$32260,a0; lea $30000,a1; ...`, i.e. a decruncher copying/unpacking to $30000); it is not directly readable and must be decrunched (stub is custom; emulate or reimplement) before analysis. The unpacked image should be dumped once for the next lane.

Diffs (A1 baseline):
- A1 vs z07 [a]: 8 sectors differ (0,1,880,881,907,909,910,911), 1717 bytes. Sector 0-1: bootblock replaced by a different bootblock (checksum 07db6fcb, contains NUKE virus-checker text "Vectors Changed - Possible virus in memory"); sectors 880/881 = root + first dir block (checksum/hash/timestamps), 907..911 = two extra zero-length blank-named directory entries (blocks 909, 910) and freed-bitmap/ghost data. No file content changes.
- A1 vs z04 (DJ99 disk 1): same boot code as stock Commodore bootblock (A1's boot area matches stock for bytes 0-61, then carries 807 nonzero junk bytes in the unused 62..1023 area; DJ99/VF boot area is zero there); different file set: `DJ99` loader (88124) instead of `BS1` and `add21k`; `Xenon2` exe unchanged; startup-sequence "DJ99\nXenon2". Almost every data sector differs because files are laid out at different blocks (77 diff runs).
- A2 vs z05 (disk 2): 3 diff runs, 26-byte total. 0x04a0e5 (sector 592+229): 0x1c -> 0x14 (1 byte); 0x0d61d7 (sector 1712+471): 000000000000 -> 100000004001; 0x0d61ea (sector 1712+490): 22 zero bytes -> `15 55 55...` (a pattern fill). Likely DJ99 data tweaks/trainer storage; treat disk 2 of the DJ99 pack as modified. Everything else is byte-identical, so disk 2 of A2 is the cleanest.
- z01 PNA vs z02 PNA[a]: 1 sector, 4 bytes at 0x78300: `53 78 0c ca` -> `4e 71 4e 71` (two NOPs, a crack patch removal of a check).
- VF vs VF[a]: 577 sectors differ (206 runs); exe `XENON_II` 197456 bytes in VF (one 197396-byte hunk) vs 174836 bytes in VF[a] (3 hunks, ends with a 174624-byte code hunk) -> different crunchers. Neither exe shares any 24-byte run with the BS1 exe, so they are packed differently or rebuilt. VF also carries files `000b00e5`, `00fa00fe`, `02020113`, `05c400f8`, `031f0159`, `04820138` (renamed data files, 60-140 KB each) i.e. the original disk-2 data split into files.
- PNA/QTX/BM boot blocks all different (custom trackloader code at boot, e.g. PNA boot `41fa0008 21c80080 4e40 ...`), root pointer 0, disk contents are loader-format and use no standard file layout; PNA disk also embeds a hidden OFS directory "Copylock Amiga Key Disk" (keydisk.s, keydisk.obj, protect, ...) at block 880.

Unused tracks: BS1 disk 1 uses track 0 and tracks 36..82; disk 2 uses tracks 0..148. PNA/BM use all 160 tracks; QTX and VF use ~140.

## Recommendation: canonical target

Canonical: the BS1 `[t +3]` pair, i.e. `generated/sources/Xenon2/Xenon II - Megablast (1of2)[t+3].adf` (SHA1 45e66f9c...) and `generated/sources/Xenon2/Xenon II - Megablast (2of2)[t+3].adf` (SHA1 a748afc7...). The same bytes also appear in the Amiga_EN archive as z06/z08.

Rationale:
- It is the only 2-disk layout that keeps disk 2 as the original-style raw data disk with game data in place, rather than re-packed/renamed (VF) or loader-formatted (PNA/QTX/BM), so addresses/offsets in the game data are closest to the retail release.
- The stock Commodore boot code and plain OFS file layout make the main exe easy to extract; and the main exe (`778cf75e...`) is identical in every BS1/DJ99 image, so it is not unique to one hack and unlikely to be modified by the BS1 trainer (the trainer lives in the separate `BS1` loader file and runs `XENON-II` after it).
- Disk 2 is untouched relative to the DJ99 variant (which has 26 modified bytes).
- Disadvantage: it is trained, and `BS1` + `add21k` run before the game. The recomp must ignore `BS1`/`add21k` (not part of the game) and start at `XENON-II` loaded in chip RAM; all trainer menu/options in the BS1 loader will be absent.

Caveats and open questions for the team:
1. No clean retail image exists in this set. We cannot prove that `XENON-II` carries no BS1 crack patches inside its packed body; confirming needs the decrunched images of `XENON-II` and the VF/PNA/QTX executables to be compared. Suggested follow-up: emulate the decrunch stub of `XENON-II` (code starts at file offset 0x24) and dump memory; do the same for the VF exe and diff.
2. The PNA/QTX/BM disks use custom loaders; use them only for cross-checking the unpacked code, not as targets.
3. Because OFS file extraction is needed, the extractor in `tools/catalog_sources.py` only hashes/diffs; file extraction was done ad hoc (OFS reader: header key block, data pointers at +24..+308 reversed, extension at +504, data blocks 24-byte header).

### What the WHDLoad imager and slave sources tell us (`whdload-de/x/Xenon2/Xenon2HD/source/`)
The Xenon 2 install supports six floppy versions plus CDTV. `xenon2.islave.s` (Wepl, public domain) records their disk layouts;
`Xenon2HD.s` selects the version by the CRC-16/ARC of the 1 KB boot block of disk 1 (`$7f8f` v1, `$c0fb` v2, `$7ea7` v3,
`$7e53` v4, `$bdce` v5, `$6827` v6). Checked here: the 0297 and 1.7 Disk.1 are v3 (`7ea7`), the 1762 Disk.1 is v2 (`c0fb`), the
2234 Disk.1 is v6 (`6827`).

| slave version | disk 1 layout | note |
|---|---|---|
| v1, v2, v3 (the two-disk **retail** releases) | track 0 standard; **track 1 Rob Northen Copylock** (some versions without); tracks 2-159 standard | disk 2: all 160 tracks standard |
| v4 | one disk, all tracks standard | budget, no intro |
| v5 | one disk, track 0 standard, tracks 1-159 **Rob Northen PDos** ($1800-byte tracks, `$1448` sync) | Bitmap Brothers zoom, budget |
| v6 | one disk, **Speedlock**: track 1 the Speedlock track, track 2 and 3-159 `$4489`-synced custom data ($1800 / $1b00 even-odd MFM + long checksum); intro = $4b170 bytes at tracks 3-47, main = $2a314 bytes at 48-73 | the Power Pack (SPS 2234) |

Consequences for the importer: (1) **the retail game contains its own Copylock checks.** The slave replays the key
(`$7670CF6B`) and patches two further checks: `patch $63e` ("second copylock") and `$4ef8763a` at `$70f6` ("third copylock");
a cracked image removes these, our BS1 image is therefore not byte-identical to the retail game code. (2) Retail disk 1 is
mostly standard sectors, so a **plain ADF holds everything except the Copylock track 1** (the 0297 WHD image stores it as a blank
`DMFM_NULL` track); the retail disk 1 has four tiny OFS-looking files (1540, 2844, 2426, 15,088 B, names of `0` characters) and
loads the game from raw offsets (e.g. `$2c00`, `$52 * $1600`). (3) v4-v6 each need their own extractor and v5/v6 a
protected-track decoder.

- Every `XENON-II` executable found in the BS1/DJ99/Timecircle ADFs is `778cf75e…`; the VF executables (`87fa47ae…`, `7b27789c…`) and the Black Monks h one (`48a31ecb…`) do not have the packed-hunk shape the importer depacks.

### IPF header facts (no decoding done in this phase)
All six Xenon 2 IPFs are well-formed CAPS record chains ending exactly at end of file: INFO encoder type 1 rev 1; retail 0297 and
2874: tracks 0-83, 168 IMGE and 168 DATA records, disk numbers 1 and 2; compilation 1762 and Power Pack 2234: tracks 0-81 (164
records), disk numbers 1/2 and 0.
