# Execution trace coverage (Phase 5b)

This file covers the replay corpus, the execution traces taken from it, and how the traced code compares with
the Ghidra code map (`ghidra-code-map.md`). The tracer is in `runtime/trace/`; CLI and tool usage are in
`docs/BUILDING.md` (section "Coverage tracing"); the corpus is described in `tests/replays/README.md`. The
data for the recompiler is in `generated/trace/` (gitignored, regenerated by
`python3 -I tools/trace/run_corpus.py`).

**Summary.**
- **Corpus:** 15 replays of 4,500 to 6,000 frames each, 86,985 frames in all. Across them the CPU executed
  about 1.0 billion instructions.
- **Coverage:** they reach **12,967 of the 15,791 instructions that Ghidra decoded (82.1 %)**. They also reach
  **879 instructions that Ghidra never decoded**, all in levels 2-5 and all object handlers.
- **Indirect sites:** 24 sites, with 273 distinct targets observed.
- **Self-modifying code:** none in any healthy run.
- **Not reached:**
  - no boss is ever defeated;
  - levels 2-5 and the ending are reached only through coverage pokes;
  - the disk loader body is replaced by the HLE shim.

## 1. Method

### Tracer

Every instruction-hook call records:
- the PC, an execution count, and the instruction length (from Musashi's disassembler, taken on first
  execution);
- the outcome of the previous instruction, based on its opcode class.

The opcode classes are handled as follows:

| Previous instruction | What is recorded |
|---|---|
| Bcc, DBcc, BRA | taken / not-taken counts and the target |
| BSR, JSR | the call; also the return address pushed, on a shadow stack indexed by stack address |
| `jmp`/`jsr` through `(An)`, `d16(An)`, `d8(An,Xn)` or `d8(PC,Xn)` | each indirect site with its targets and counts |
| RTS, RTR | when the popped address is not the one the matching call pushed, the site is an "rts used as a jump" and its targets are recorded the same way |

- **Rts used as a jump.** This finds `obj_call_handler_a` (`$5924`: `move.l $A(a1),-(sp); rts`, the `rts`
  at `$5928`) with no prior knowledge. No other site in the game or its modules does this.
- **Interrupts.** An interrupt entry is a PC equal to the autovector target of the current mask level, where
  the stacked SR had a lower mask. The previous instruction's successor is then taken from the stacked PC, so
  branch statistics are not corrupted by interrupts.
- **HLE redirects.** The disk shim's trap at `$921A` moves the PC. Musashi runs the next instruction without
  calling the hook, so the tracer records that instruction itself.
- **Writes into code.** Every CPU write (`Machine::write8/16`) and every blitter area-mode D range is checked
  against the bytes of already-executed instructions. Line-mode blits are not checked; the game never uses
  them. Separately, each execution compares the opcode word with the one seen the first time at that PC. That
  check catches changes from any source, including disk loads and DMA.
- **Overlay attribution.** PCs in `$54E00-$7FFFF` are attributed to the module the disk shim last loaded at
  `$54E00`:
  - the key is an FNV-1a 64 hash of the module's first 8 KB, so a module reloaded with fewer sectors after
    the shop keeps its identity;
  - the name comes from the level table at `$91EA`.

  Each module has its own executed-byte map, so module A's code is never confused with module B's data at
  the same address.

The cost when tracing is off is one null-pointer test per instruction and per CPU write. All CTests, including
`golden_frames` and the 15 `replay_*` hash tests, give identical results with and without `--trace-out`.

## 5. Self-modifying code

**There is none in any run of the corpus:**
- 0 CPU writes into executed bytes;
- 0 blitter writes into executed bytes;
- 0 opcode changes at an executed PC.

This holds across all 15 replays, including the shop overlay swapping in and out and modules reloaded with
fewer sectors.

The detector is known to work. It flagged every corrupted plan variant that was rejected while the corpus was
built (`tests/replays/README.md`, "Health rules"). For example, the level-3 run that moved the scroll position
under the clamp `$CE8` gave these two reports:

```
code_writes: level3 $54E0C written by the blitter (started at $1832, blit_objects_main), 146,320 bytes, frame 3704
code_changes: level3 $54E24 $6000 -> $7032 at frame 3705   (then: illegal instruction -> restart via $7032)
```

That is a consequence of the poke, not of the game. Together with section 6 of `ghidra-code-map.md`, this
confirms that the game neither patches nor generates code at run time. The anti-trace block `$7104-$763A`
never executed.

## 6. Interrupts

Only two interrupt entry points were ever taken:

- **L3 VBL `$20C2`:** 86,970 entries, one per frame.
- **L2 keyboard `$0FAC`:** 8 entries, one per key edge in `menu_2p`.

These handlers were never entered:

- **`$2098` (`irq3_vbl_diskload`):** installed only while a disk load runs, and the shim finishes a load inside
  one instruction.
- **`$95E4` (`irq1_dskblk`):** DSKBLK is never raised.

## 8. Honesty notes and known gaps

- **Pokes.**
  - Levels 2-5, the ending and the shop with large cash are reached only through coverage pokes (section 2).
    So are the fast-forwards and jumps through the levels.
  - Only `attract`, `menu_2p` and `level1_play` use plain input.
  - Code reached under pokes is real game code running on the game's own paths (end-of-level, shop request,
    ending flag). The states that lead there are not natural, though: the enemy mix differs, and some events
    are skipped or bunched together.
- **Not reached at all:** a boss defeat, the natural end of a level, and the level-5 ending reached by
  playing.
- **Rejected plan variants.** Three crashed the game (`tests/replays/README.md`, "Health rules"). All three
  were traced to the pokes:
  - an event flood that exhausted the object pool;
  - a scroll position below the clamp;
  - a level-5 position jump.

  None is evidence of a runtime bug. The level-3 flood replay is left out for that reason.
- **The coverage percentage** counts instruction start addresses in Ghidra's listing. Ghidra decoded some
  bytes that look like code but are not reachable. For example, `$54E00` in levels 1-5 is a header of data
  longs decoded as `ori.b`.
